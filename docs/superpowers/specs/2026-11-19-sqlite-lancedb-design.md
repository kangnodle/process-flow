# SQLite 기준 저장소와 LanceDB 검색 전환 설계

## 목적과 범위

SurrealDB가 담당하는 영속 저장과 검색을 SQLite와 LanceDB로 분리한다. SQLite는 업무 데이터의 원본이고 LanceDB는 SQLite에서 재생성할 수 있는 검색 색인이다. 사용자는 이 조합을 선택했다. LadybugDB는 도입하지 않는다.

기존 HTTP 경로, JSON 형식, 인증, 권한, 순차 진행, 문서와 파일 증빙, RACI 배정, 낙관적 버전 검사를 유지한다. 검색은 현재의 해시 임베딩과 코사인 유사도를 유지한다. 검색 엔진 변경에 따른 근사 검색 결과의 완전한 일치는 보장하지 않지만 검색 범위, 점수 의미와 정렬 계약은 유지한다.

사용자가 새 SQLite 데이터로 시작하기로 결정했다. 기존 SurrealDB 데이터 이관과 스냅샷 가져오기는 이번 범위에서 제외한다. 기존 데이터 경로는 수정하거나 삭제하지 않는다.

## 검토한 접근

| 접근 | 장점 | 비용과 선택 |
| --- | --- | --- |
| SQLite 단독 | 저장소와 복구 경로가 단순함 | 벡터 검색을 별도로 구현해야 함 |
| SQLite와 LanceDB | 업무 트랜잭션과 벡터 검색의 책임을 분리함 | 색인 동기화가 필요함. 사용자가 선택한 접근 |
| SQLite와 LanceDB와 LadybugDB | 그래프 질의까지 별도 엔진으로 확장 가능 | 현재 순차 공정에는 추가 저장소와 동기화 비용이 큼 |

## 현재 구조와 변경 경계

`backend`는 Cargo workspace이며 `core/domain`은 도메인 모델, `core/application`은 정책과 포트, `runtime`은 유스케이스 실행, `adapters`는 포트 구현, `apps/server`는 조립을 담당한다. 프론트엔드는 별도의 npm workspace다.

현재 SurrealDB 어댑터는 공정, 프로젝트, 사용자와 자격 증명, 세션, 멤버십, 워크플로, 배정, 화면 설정, 검색 색인을 구현한다. 워크플로 변경은 상태, 감사 이벤트, `index_job`을 같은 트랜잭션에 저장한다. 프로젝트 삭제는 검색 색인까지 같은 DB에서 제거한다. 이 보장을 두 DB를 넘는 하나의 트랜잭션으로 옮기려고 해서는 안 된다.

`RecordIndex`는 현재 검색과 작업 큐 처리 책임을 함께 갖는다. 이를 검색 색인 포트, 내구성 있는 색인 작업 저장소 포트, 원본 검색 문서 조회 포트로 나눈다. 포트에는 도메인 식별자, 텍스트, 숫자, 벡터와 오류만 노출한다. SQLx, Arrow, LanceDB 타입은 어댑터 밖으로 노출하지 않는다.

## 패키지와 의존성

- `process-flow-adapter-sqlite`: 기존 저장소 포트, 공정 조회, 검색 원본과 작업 큐를 구현한다.
- `process-flow-adapter-lancedb`: 벡터 문서 저장, 삭제, 검색과 색인 상태 조회를 구현한다.
- `process-flow-application`: DB와 무관한 검색 문서와 작업 포트를 정의한다.
- `process-flow-runtime`: 임베딩, 큐 처리, 검색 결과의 원본 검증과 복구 순회를 포트로 조율한다.
- `apps/server`: 설정, 저장소 잠금, 어댑터 생성과 작업자 수명 주기를 조립한다.
- `process-flow-testing`: 새 포트에 맞춘 결정적인 메모리 대역을 제공한다.

SQLite 접근은 기존 비동기 실행 구조에 맞춰 SQLx를 사용한다. LanceDB와 필요한 Arrow 의존성은 LanceDB 어댑터에만 둔다. 정확한 크레이트 버전은 현재 고정된 Rust 1.98.0으로 의존성 호환성을 확인한 후 잠금 파일에 고정하는 구현자 결정이다. 단순 저장소 교체를 위해 도메인 모델이나 프론트엔드 계약을 변경하지 않는다.

## SQLite 데이터 모델과 트랜잭션

버전이 있는 SQL 마이그레이션을 적용한다. 파일 DB는 WAL, 연결별 외래 키 검사, 유한한 잠금 대기 시간을 명시적으로 설정한다. 쓰기 트랜잭션 안에서 임베딩 생성이나 LanceDB 호출을 하지 않는다.

| 데이터 | 저장 형태와 제약 |
| --- | --- |
| 공정, 단계, 작업 | 텍스트 식별자와 부모 외래 키, 단계 순서와 작업 번호의 고유 제약 |
| 프로젝트, 사용자 | 검색 가능한 일반 열, 이메일 고유 제약, 음수가 아닌 버전 |
| 자격 증명, 세션, 초기 관리자 표식 | 해시와 기존 만료 시간, 사용자 외래 키, 원자적인 최초 관리자 생성 |
| 멤버십 | 사용자와 프로젝트의 복합 고유 키, 역할 검사 |
| 워크플로 | 프로젝트와 공정 외래 키, 진행 상태, 버전과 시간 |
| 작업 기록 | 워크플로와 작업의 복합 키, 링크와 메모, 문서와 증빙 JSON, 검색 문서 개정 식별자 |
| 감사 이벤트, 배정 변경 이력 | 기존 실행자, 실행 근거, 버전, 시간과 내용 보존 |
| 배정, 화면 설정 | 개별 버전 또는 필드별 병합 계약 유지, 구조화 데이터는 검증한 JSON으로 저장 |
| 검색 작업 | 원본과 함께 커밋하는 작업 식별자, 대상, 개정, 종류, 텍스트, 시도 횟수와 다음 시각 |

워크플로 저장은 `expected_version` 조건부 갱신의 영향 행 수를 확인하고, 기록과 이벤트와 색인 작업까지 한 번에 커밋한다. 실패하면 모두 롤백한다. 배정 변경과 이력, 프로젝트 생성과 소유자 등록도 각 저장소 메서드의 기존 원자성을 유지한다. 보관 프로젝트 삭제는 종속 업무 데이터를 원자적으로 삭제하고, LanceDB 삭제 작업을 같은 트랜잭션에 남긴다. 삭제 작업은 원본 행의 외래 키 연쇄 삭제로 사라지지 않아야 한다.

선행 작업 조회는 해당 작업보다 앞선 단계의 작업을 번호순으로 반환한다. 같은 단계의 앞선 작업을 추가하는 등 기존 그래프 조회 의미를 바꾸지 않는다. 워크플로 목록은 증빙과 전체 작업 문서를 읽지 않는 기존 최적화를 유지한다.

## LanceDB 검색과 동기화

LanceDB 문서는 워크플로 ID, 작업 ID, 검색 문서 개정 식별자, 텍스트와 고정 차원 벡터를 갖는다. 개정 식별자는 SQLite에서 발급하는 영속적인 단조 증가 값이며, 재시도에서는 유지하고 검색 대상 텍스트가 바뀌면 새로 발급한다. 일반 상태 변경만으로 검색 문서를 무효화하지 않는다.

코사인 거리로 검색하고 API에는 코사인 유사도를 반환한다. 유효한 유사도만 내림차순으로 반환하고 기존의 양수 점수 조건과 최대 50개 제한을 유지한다. 기존 임베더와 기본 256차원을 유지한다. 영벡터 검색은 빈 결과로 처리하고 영벡터 문서는 검색 대상에서 제외한다. 차원이나 임베딩 버전이 색인 메타데이터와 다르면 명확한 재구축 안내와 함께 실패하고 기존 색인을 조용히 덮어쓰지 않는다.

허용된 워크플로 범위로 검색 후보를 제한하고, 반환 전 SQLite 원본의 존재와 현재 개정을 검사한다. 원본에서 삭제되거나 갱신된 문서의 이전 텍스트는 반환하지 않는다. 필터와 값 바인딩은 문자열 식별자에 의한 쿼리 주입이 불가능한 방식으로 구현한다. 오래된 후보를 제거한 뒤 결과가 부족하면 후보 범위를 늘려 유효한 결과를 채우거나 후보 소진 시 종료한다.

작업 처리 순서는 다음과 같다.

1. SQLite에서 처리할 작업과 개정을 읽는다. 동일 문서의 대기 작업은 최신 상태로 합칠 수 있다.
2. 트랜잭션 밖에서 임베딩을 만들고 LanceDB에 문서를 upsert하거나 삭제한다.
3. SQLite에서 처리한 작업 식별자와 개정이 여전히 같을 때만 완료 처리한다. 새 작업을 이전 작업의 완료 처리로 지우지 않는다.
4. 실패하면 재시도 횟수와 지수 대기 시간을 영속 저장한다. 한 문서 실패가 다른 문서 처리를 막지 않게 한다.

이 초기 구현은 로컬 데이터 경로당 서버 프로세스 하나를 지원한다. 시작 시 OS 파일 잠금으로 두 번째 서버나 재구축 도구의 동시 쓰기를 거부하고, 프로세스 안의 LanceDB 쓰기는 하나의 작업자로 직렬화한다. HTTP 워커는 여러 개일 수 있다. 잠금은 프로세스 종료 시 해제되는 방식이어야 한다.

LanceDB 쓰기 성공 후 SQLite 완료 처리 전에 종료되어도 동일 작업을 반복할 수 있어야 한다. 처리 중 새 저장이나 프로젝트 삭제가 발생하면 이전 결과는 원본 검증으로 숨기고 최신 upsert 또는 삭제 작업으로 수렴한다. 저장 완료 응답은 SQLite 커밋을 의미하고, 검색 반영은 기존과 같이 비동기다. LanceDB 장애로 이미 커밋한 업무 저장을 실패로 보고하지 않는다.

## 복구와 운영

현재 복구 순회의 페이지 처리와 개별 오류 격리를 유지한다. 원본과 색인의 키와 개정을 비교해 누락, 불일치, 불필요한 문서를 처리하는 작업을 등록한다. 오래된 원본 스냅샷은 현재 개정을 다시 확인한 뒤에만 작업을 등록하며 최신 대기 작업을 덮어쓰지 않는다.

색인 디렉터리가 없으면 새 색인을 만들고 SQLite 기록에서 검색을 복원한다. 재구축 명령은 서버를 중지한 상태에서 같은 OS 잠금을 획득한 뒤 실행한다. SQLite를 기준으로 새 LanceDB 디렉터리를 만들고 검증이 끝난 뒤 전환한다. 초기 재구축 동안 검색 결과가 부분적일 수 있음을 운영 문서에 명시한다.

정상 종료는 새 작업을 중단하고 진행 중인 쓰기를 마친 뒤 저장소를 닫는다. 강제 종료는 미완료 작업을 다음 시작에서 재실행한다. 기본 경로는 `SQLITE_URL=sqlite://data/process-flow.sqlite3`, `LANCEDB_URI=data/search.lancedb`다. 기존 SurrealKV 경로를 새 형식으로 열거나 삭제하지 않는다.

백업의 필수 대상은 SQLite 원본이다. 온라인 백업 API 또는 서버 중지 후 안전한 복사를 사용한다. WAL이 활성화된 실행 중 DB의 본체 파일만 복사하지 않는다. LanceDB는 재생성 가능하며 필요하면 서버 중지 후 별도로 보관한다.

## 새 데이터로 시작

기본 SQLite와 LanceDB 경로에 새 저장소를 생성한다. 최초 실행에서 관리자를 설정하고 업무 데이터를 새로 작성한다. 미구현 스냅샷 가져오기 명령과 테스트를 제거한다. 사용하지 않는 기존 추출 도구도 제거한다.

## 검증 기준

- 공정 왕복 저장과 선행 작업 결과가 기존 동작과 같다.
- 프로젝트, 사용자, 세션, 멤버십, 배정, 화면 설정의 저장 계약과 오류 매핑을 실제 SQLite로 검증한다.
- 동시 버전 갱신에서 한 요청만 성공하고, 실패한 트랜잭션의 상태와 이벤트와 작업이 남지 않는다.
- 최초 관리자 동시 생성은 하나만 성공하고 자격 증명이 원자적으로 저장된다.
- 문서, 파일 증빙과 감사 이력이 프로세스 재시작 후 복원된다.
- 실제 LanceDB에서 코사인 점수, 순위, 워크플로 범위, 빈 범위, 영벡터와 차원 오류를 검증한다.
- 저장 중 색인 갱신, 삭제 중 작업 실행, 오래된 작업 완료, 반복 실행, 장애 후 재시작에서 이전 데이터가 검색되지 않는다.
- LanceDB 반영 직후 강제 종료하는 경우에도 재시도와 복구가 수렴한다.
- 색인 삭제와 손상, 누락과 불일치 문서, 페이지를 넘는 복구와 개별 실패를 검증한다.
- 두 서버 프로세스의 같은 저장소 사용을 거부하고 종료 후 다시 시작할 수 있다.
- `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`와 실제 서버 재시작 통합 테스트를 실행한다.

## 완료 범위와 구현자 결정

서버의 SurrealDB 의존성과 설정을 제거하고 README, 환경 변수 예제, 벤치마크 실행 예제, 개발용 DB 실행 안내를 갱신한다. SurrealDB 때문에 추가된 툴체인과 빌드 옵션은 이유와 실제 검증 결과에 따라 정리하며 이 작업만으로 컴파일러를 임의 업그레이드하지 않는다. 소스 코드에 설명 주석을 추가하지 않는다.

정확한 테이블 이름, SQL과 행 변환 모듈의 분할, 호환 크레이트 버전, 연결 풀 크기, 검색 색인 알고리즘과 생성 기준은 구현자가 결정한다. 작은 데이터에서는 정확 검색을 허용하고 규모가 커지면 같은 검색 계약 안에서 근사 색인을 생성한다. 검색 품질 개선용 새 임베딩 모델, 다중 서버 동시 쓰기, 클라우드 서비스, 공정 DAG 확장과 화면 개편은 범위에 넣지 않는다.
